# Part 2 后端常用技术栈 — Redis

## 1. Redis 是什么？为什么后端需要它？

Redis 是一种主要基于内存工作的数据存储系统，常用于缓存、计数等场景。它不只是“能存字符串的数据库”，也提供 Hash、List、Set 等多种数据类型。

JotangNote 中如果大量用户反复查看同一篇笔记，每次都查询 MySQL 会增加数据库负担。可以先从 Redis 读取：缓存命中时直接返回；未命中时查询 MySQL，再将结果缓存到 Redis。这样通常能降低重复查询的耗时和 MySQL 的访问压力。

MySQL 可以作为主要业务数据的持久化存储；Redis 常用于保存可以按需重新获取的热点数据。两者并不是相互替代的关系。

## 2. Key-Value、String 与 Hash

Redis 最外层通过 Key 找到对应的 Value，但不同 Key 的 Value 可以采用不同数据类型。最外层用 Key 查找数据的实现方式，与“Value 的类型叫 Hash”是两个不同概念。

### String：一个整体值

```redis
SET note:5:string "Redis学习笔记"
GET note:5:string
```

String 可以理解为一个 Key 对应一个完整值。对已有 String 再用 SET，会覆盖旧值。

### Hash：一个 Key 下包含多个 Field-Value

```redis
HSET note:5:hash title "Redis基础" author "golds" content "学习Redis"
HGET note:5:hash author
HSET note:5:hash title "Redis进阶"
```

Hash 适合按字段读取或修改，例如只修改标题，不用重新写入作者和正文。

一个 Key 在某一时刻只有一种数据类型，不能直接对 String 使用 HGET；否则会出现 WRONGTYPE。可用 `TYPE key` 查看类型。上述例子故意使用不同的 Key，避免类型冲突。

## 3. TTL 和过期删除

```redis
SET note:5 "Redis学习笔记" EX 60
GET note:5
```

`EX 60` 表示设置 60 秒的有效期。过期之后，正常读取不会返回旧值；但数据从“逻辑过期”到“物理删除并释放内存”不必恰好在同一时刻完成。

Redis 主要配合以下机制：

- **惰性删除**：访问某个 Key 时发现已过期，就将其视为失效并清理；
- **定期主动删除**：后台周期性检查一部分带过期时间的 Key，主动清理过期数据。

这不同于“给每个 Key 单独安排一个到点必执行的定时器”。课堂讨论中还对比了自写 C-KV 的最小堆思路：若只在处理请求时检查堆顶，而没有后台任务，那么在完全没有请求的期间，已过期条目未必会被立刻物理清理。

## 4. MySQL 与 Redis 如何配合？（Cache-Aside）

读操作的一种常见流程：

1. 先查询 Redis；
2. 命中则直接返回缓存；
3. 未命中则查询 MySQL；
4. 将查询结果写入 Redis，并设置合理 TTL，然后返回。

修改笔记时的一种常见策略：

1. 先完成 MySQL 的数据修改；
2. 修改成功后，删除对应的 Redis 缓存；
3. 下一次查询发现缓存未命中，再从 MySQL 获取最新数据并重新缓存。

“删除缓存而不是立刻更新缓存”的一个原因是：修改后的笔记不一定很快有人查看；按需重新缓存可以避免无用的缓存更新。

## 5. 缓存一致性问题

假设 MySQL 已是“第二版”，Redis 仍保存“第一版”。如果用户的查询一直命中 Redis，就可能持续获得旧版本（stale data）。

如果 Python 后端在完成 MySQL 更新后、删除 Redis 缓存之前崩溃，MySQL 与 Redis 可能暂时不一致。TTL 能限制旧缓存继续有效的时间，但不能保证缓存到期之前的数据是最新的。删除失败重试等机制可以降低风险；实际并发情况下还存在更复杂的一致性问题。

“旧数据”和“过期数据”并不一样：

- 旧数据：相对 MySQL 的最新状态已经落后，但 Redis 的 TTL 可能还没结束；
- 过期数据：已经到达 TTL，正常读取不会再获取该值。
