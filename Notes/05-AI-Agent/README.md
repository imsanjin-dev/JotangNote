# Part 2 后端常用技术栈 — AI Agent

## 1. AI Agent 是什么？

普通大语言模型（LLM）主要根据输入的上下文生成文本。本身并不会因为回答了“我已查询数据库”，就真的访问过数据库。

AI Agent 可以理解为以模型为推理核心、结合工具调用和执行流程的应用。模型负责理解需求、决定下一步操作；外部程序负责执行实际操作，再把结果返回模型。

以 JotangNote 为例，Agent 可以根据用户要求查找笔记、总结内容或者管理学习记录。它能做到这些，不是因为模型天然具有数据库访问权限，而是因为后端提供了相应的工具。

## 2. Agent 如何调用工具执行操作？

一种常见实现是 **Tool Calling（工具调用）**，也常叫 Function Calling。

以“查找 Redis 笔记”为例：

1. 后端向模型提供可用工具的名称、功能描述和参数结构，例如 `search_notes(keyword: str)`；
2. 模型根据用户需求，返回调用 `search_notes` 并传入 `keyword="Redis"` 的结构化请求；
3. **后端程序**检查用户权限、参数及操作是否允许，再执行对应 Python 函数；
4. 函数访问 MySQL 等外部系统，把实际查询结果交还给模型；
5. 模型根据结果生成最终回答；必要时还可继续请求其他工具。

关键区别：**模型提出 Tool Call，不等于工具已经执行。真正执行的是 Agent 所在的后端或工具运行环境。**

工具可以是我们自己编写的 Python 函数，也可以是接入的外部服务，不一定需要做成独立插件。MCP（Model Context Protocol）则提供了一种标准化的工具和上下文接入方式；直接使用模型的 Function Calling 并不要求自己搭建 MCP Server。

### 工具调用的安全边界

不能因为模型提出调用，就直接执行所有操作。后端需要验证参数、用户身份和访问权限。删除大量笔记等有破坏性的操作还应要求用户明确确认，必要时提供撤销或恢复机制。

模型可能判断错误，也可能受到不可信笔记内容的干扰。因此工具权限应限制在真实业务需要的范围内，避免让模型决定自己的权限。

## 3. Agent 的上下文有限，如何实现长期记忆？

模型一次能处理的上下文长度有限，不能把用户长期以来的全部对话、笔记和操作记录一直放进提示词。

一种解决方案是 **外部存储 + 摘要 + 按需检索**：

- **外部存储**：把学习记录、原始对话及摘要等保存到 MySQL 等持久化存储中，而不是只依赖当前对话窗口；
- **摘要压缩**：每次学习后提取已经掌握的内容、目前的疑问和下一步方向，减少需要重复读取的信息；
- **按需检索**：用户提出新问题时，根据用户、主题和时间等条件查找相关记录；
- **注入上下文**：只把与当前问题相关的摘要或原始片段提供给模型，辅助生成回答。

例如，用户一个月前学习了 Redis 的 String 与 Hash，一个月后询问“我上次学到哪里了？”，后端可以查询 Redis 学习摘要并交给模型，模型再据此回答。

摘要不一定完全准确，也可能已经过时，因此应尽量保留可追溯的原始记录；遇到冲突或重要细节时，再回查原始内容。Redis 可以用于缓存近期或频繁访问的会话数据，但缓存不应被误认为天然可靠的长期记忆。

关键是把历史内容保存在外部，再根据当前问题按需取回；这不等于模型参数本身拥有了长期记忆。

## 4. 在 JotangNote 中可以怎样实现？

一个简单的学习助手可以包含：

- **笔记工具**：按关键词或笔记 ID 查询内容；
- **学习摘要**：在一次学习结束后保存掌握情况、知识断点和后续计划；
- **历史检索**：结合主题、时间与用户身份查找相关摘要，必要时回查原文；
- **回答生成**：将可靠的检索结果交给模型，让模型整理成自然语言。

JotangNote 当前实现了按笔记 ID 查询的工具；学习摘要和历史检索尚未实现。
